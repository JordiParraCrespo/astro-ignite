# Internationalisation (i18n)

The starter uses Astro's native i18n with **parallel routes** — every page under `src/pages/` exists twice: once at the top level (default locale) and once inside `src/pages/[lang]/` (all other locales). This section explains how the system works and how to extend it.

## Configuration

All locale settings live in `src/config/site.ts`:

```ts
export const siteConfig = {
  locales: ['en'],          // add more here: ['en', 'es', 'fr']
  defaultLocale: 'en',
  // per-locale metadata
  name: { en: 'My Site', es: 'Mi Sitio' },
  description: { en: '...', es: '...' },
  organization: {
    en: { name: 'Acme Inc.', legalName: 'Acme Inc.' },
    es: { name: 'Acme S.L.',  legalName: 'Acme S.L.' },
  },
};
```

The default locale ships as `['en']` — parallel routes inside `[lang]/` are dormant until you add a second locale.

## Route pattern

```
src/pages/
├── index.astro            # /                  (default locale)
├── about.astro            # /about
├── blog/
│   ├── index.astro        # /blog
│   └── [...slug].astro    # /blog/<slug>
└── [lang]/                # /es/, /fr/, etc.
    ├── index.astro        # /es/
    ├── about.astro        # /es/about
    └── blog/
        ├── index.astro    # /es/blog
        └── [...slug].astro  # /es/blog/<slug>
```

The `[lang]` directory name is canonical — do not rename it to `[locale]` or `[language]`. Inside every `[lang]` route file, read the locale from `Astro.params.lang`.

Every `[lang]/*` file must export `getStaticPaths` that emits one entry per non-default locale:

```ts
export function getStaticPaths() {
  return siteConfig.locales
    .filter(l => l !== siteConfig.defaultLocale)
    .map(lang => ({ params: { lang } }));
}
```

## Internal links

Always build URLs through `getRelativeLocaleUrl` — never hardcode paths:

```astro
---
import { getRelativeLocaleUrl } from 'astro:i18n';
const { lang } = Astro.params; // undefined on default-locale routes
---

<a href={getRelativeLocaleUrl(lang ?? siteConfig.defaultLocale, '/about')}>
  About
</a>
```

On default-locale pages, `lang` is `undefined` (not in the URL) — fall back to `siteConfig.defaultLocale` before passing to the helper.

## UI strings

Per-locale UI strings (nav labels, button text, date formats) live in `src/i18n/<locale>.json`. Load them via the `t()` helper:

```ts
import { useTranslations } from '@/i18n';

const t = useTranslations(lang ?? siteConfig.defaultLocale);
// then:
t('nav.blog')   // → "Blog" or "Blog" (translated value for that key)
```

Add a new key:

1. Add the key + English value to `src/i18n/en.json`
2. Add translated values to every other locale file
3. Reference via `t('your.new.key')` in components

## Content collections

Blog, projects, and legal content use a `{locale}/{slug}` folder layout:

```
src/content/
├── blog/
│   ├── en/                # src/content/blog/en/*.mdx
│   └── es/                # src/content/blog/es/*.mdx
├── projects/
│   ├── en/{slug}/index.mdx
│   └── es/{slug}/index.mdx
└── legal/
    ├── en/{privacy,terms,cookies}.mdx
    └── es/{privacy,terms,cookies}.mdx
```

The route files (`/blog/[...slug].astro` and `/[lang]/blog/[...slug].astro`) filter the collection by locale prefix:

```ts
const posts = await getCollection('blog', e => e.id.startsWith(`${lang}/`));
```

When translating content, copy the source file to the target locale folder and translate the body + frontmatter `title` / `description`. The slug (filename without extension) determines the URL — keep it the same across locales so canonical links work.

## Adding a locale

1. **`src/config/site.ts`** — add the locale code to `siteConfig.locales`:
   ```ts
   locales: ['en', 'es'],
   ```
   Add locale-keyed values for `name`, `description`, `organization`:
   ```ts
   name: { en: 'My Site', es: 'Mi Sitio' },
   ```

2. **`src/i18n/<locale>.json`** — copy `en.json`, translate every value.

3. **Content** — copy `src/content/blog/en/*.mdx` to `src/content/blog/es/` and translate.

4. **Legal pages** — copy `src/content/legal/en/*.mdx` to `src/content/legal/es/` and translate.

5. **OG image** (optional) — add `public/og/og-es.png` and update `siteConfig.defaultOgImage`.

6. **Verify** — run `pnpm build`. Astro will error on any `getStaticPaths` that emits entries for locales that don't match `siteConfig.locales`.

## LocaleSwitcher

The `<LocaleSwitcher>` in the header unconditionally lists every locale in `siteConfig.locales` and links to the equivalent page in that locale — there's currently no per-page prop to hide an entry, so if a page doesn't have a translated version yet (e.g. a blog post translated into English only), the switcher still links to the target locale's page and it's the author's responsibility to provide the translated content.

`SEO.astro`'s `alternates` prop only controls the `hreflang` `<link>` tags in `<head>` — pass it explicitly when a page's slug differs across locales; it has no effect on the switcher UI.

## RSS feeds

Each locale gets its own RSS feed:

- Default locale → `/rss.xml` (`src/pages/rss.xml.ts`)
- Other locales → `/<lang>/rss.xml` (`src/pages/[lang]/rss.xml.ts`)

The feed is filtered to the requesting locale's blog posts.

## Sitemap

`@astrojs/sitemap` is configured in `astro.config.mjs` and automatically emits `<xhtml:link rel="alternate">` hreflang tags for all locales. No manual sitemap configuration needed.

## Common mistakes

- **Hardcoded paths** (`href="/about"`) break non-default locales — always use `getRelativeLocaleUrl`.
- **Missing `[lang]` mirror** — adding a route under `src/pages/` without a matching file in `src/pages/[lang]/` makes the page untranslatable. The build won't error, but the locale switcher will emit a dead link.
- **Mismatched slugs** — a blog post at `en/my-post.mdx` and `es/mi-publicacion.mdx` produces different URLs. Keep slugs identical across locales.
