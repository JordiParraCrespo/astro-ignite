The CLI is intentionally small. Five questions, then a finished site — everything else lives in code you own, after the install.

## 1. Project name

Used as the folder name and the default `name` field in `package.json`. Validated against npm naming rules at the prompt.

<Callout variant="note">
  You can pass the name as the first positional arg to skip this prompt entirely: `npm create
  astro-ignite@latest my-site`.
</Callout>

## 2. Languages

Pick one or many. Sets `i18n.locales` in `astro.config.mjs` and generates locale-scoped routes, content collections, and sitemap entries. Monolingual sites get a clean tree (no locale prefix); multilingual sites get the `[lang]/...` parallels automatically.

## 3. Email provider

Three choices: **Resend** (default), **SMTP**, or **None**. Only the chosen transport's code lands in `src/lib/email/`. Switching later is a one-file edit.

## 4. Analytics

Today: Plausible-only, env-gated. Future: pick at scaffold time. The `PUBLIC_PLAUSIBLE_DOMAIN` env var activates analytics; until set, nothing fires.

## 5. Install + git

Quick yes/no on whether to run `<pm> install` and `git init` after scaffolding. Default yes for both, but `--no-install` and `--no-git` flags exist for CI use.

## What it deliberately doesn't ask

- **CSS framework** — Tailwind v4 only. Other choices fork the perf story.
- **TypeScript** — always yes. No good reason to skip in 2026.
- **Component library** — there isn't one. The kit grows via `astro-ignite add` later (post-1.1).
- **CMS** — Astro Content Collections is the answer. CMS adapters arrive as recipes, not first-class.

The point isn't to ask every possible question. It's to ask the few that meaningfully change the file tree, and to commit on everything else.
