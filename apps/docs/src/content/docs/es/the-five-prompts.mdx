El CLI es intencionadamente pequeño. Cinco preguntas y luego un sitio terminado — todo lo demás vive en código que tú posees, después de la instalación.

## 1. Nombre del proyecto

Se usa como nombre de carpeta y como valor por defecto del campo `name` en `package.json`. Validado contra las reglas de nomenclatura de npm.

<Callout variant="note">
  Puedes pasar el nombre como primer argumento posicional para saltarte este prompt:
  `npm create astro-ignite@latest mi-sitio`.
</Callout>

## 2. Idiomas

Elige uno o varios. Configura `i18n.locales` en `astro.config.mjs` y genera rutas, colecciones de contenido y entradas de sitemap por idioma. Los sitios monolingües obtienen un árbol limpio (sin prefijo de idioma); los multilingües obtienen los paralelos `[lang]/...` automáticamente.

## 3. Proveedor de email

Tres opciones: **Resend** (predeterminado), **SMTP** o **Ninguno**. Solo el código del transporte elegido aparece en `src/lib/email/`. Cambiar después es la edición de un archivo.

## 4. Analítica

Hoy: solo Plausible, controlado por variable de entorno. Futuro: elección al hacer scaffold. La variable `PUBLIC_PLAUSIBLE_DOMAIN` activa la analítica; hasta que se configure, no se ejecuta nada.

## 5. Instalar + git

Sí/no rápido sobre si ejecutar `<pm> install` y `git init` después del scaffolding. Por defecto sí en ambos casos, pero existen los flags `--no-install` y `--no-git` para uso en CI.

## Lo que intencionalmente NO pregunta

- **Framework CSS** — solo Tailwind v4. Otras opciones rompen la promesa de rendimiento.
- **TypeScript** — siempre sí. No hay buena razón para saltarlo en 2026.
- **Biblioteca de componentes** — no la hay. El kit crece vía `astro-ignite add` después (post-1.1).
- **CMS** — la respuesta son las Content Collections de Astro. Los adaptadores CMS llegan como recetas, no como ciudadanos de primera clase.

El objetivo no es preguntar todo lo posible. Es preguntar las pocas cosas que cambian materialmente el árbol de archivos y comprometerse con lo demás.
